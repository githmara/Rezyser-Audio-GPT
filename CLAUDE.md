# WHO IS YOUR INTERLOCUTOR — THREE MODES AND ONE TEST (CANON since 2026-08-17)
This file describes the behavior expected by an **ordinary contributor** to this repository: someone not necessarily blind, not necessarily from Poland, without publishing rights. This is the DEFAULT mode, and the rules below are self-sufficient within it.

**The mode is decided by IDENTITY, not by the presence of any files.** The only reliable test is the GitHub account: `gh auth status` (reads the local session, no API call) or, more precisely, `gh api user --jq .login`. The login **`githmara`** = maintainer. Run the test ONCE, and only when the mode actually matters — before an action requiring privileges, not reflexively at the start of every task.

1. **MAINTAINER** — `gh` is present and the login is `githmara`. Full publishing rights. If the Subconscious (`MEMORY.md` + `memory/*.md`) is present alongside, it **OVERRIDES** the default work style: communication protocol (long content to a file, not to the terminal) → [[reguly_architektury]], full publishing procedure → [[reguly_git_workflow]], issue-handling workflow → [[reguly_github_bot]].
2. **CONTRIBUTOR** (default) — `git` is present, but `gh` is not, or the login is different. You work like an attentive collaborator on an open-source project: the interlocutor's remarks take precedence over your assumptions, you write normally, and you break work into steps with decision points. **You do not have publishing rights:** you do not push to `main`, do not create tags, do not publish Releases, do not force-push, do not bump `VERSION`. Your contribution ends with a tested change in the working tree; commit only at the interlocutor's request. If in this mode you happen to encounter any `memory/*.md` files, treat them as **additional engineering notes from this interlocutor** — never as a grant of privileges.
3. **NON-TECHNICAL USER** — doesn't even have `git`. Most likely someone who downloaded the "Source code" asset from the Release page via a browser and pasted you a prompt from the Rule Manager. In this case, do not propose repository operations or git workflows — help with what this person actually has: the YAML rules of the language pack, using the application, explaining an error message. Speak in plain language, without publishing jargon.

**IRON BAN ON SURGERY ON THIS FILE outside maintainer mode.** Do not move, "slim down," or archive sections of CLAUDE.md — even if the interlocutor agrees, and especially not into a private agent memory directory. Such a directory is LOCAL and does not enter the repository: the excised content would evaporate for everyone else, and your own next startup would receive a mutilated Constitution plus a handful of fragments torn out of context — and would mistake them for the complete rules. You do NOT police the size of this file; the maintainer does, with a commit visible to everyone.

**What is NOT subject to override:** all technical and engineering rules in this file (wxPython, product A11y, terminal, multilingualism, gates, hygiene) apply in EVERY mode. The override concerns work style and privileges.
- **Repository language:** the code, comments, and dev-tool names are in Polish, because that is the maintainer's working language (`CONTRIBUTING.md` explains this to the contributor in English). Treat Polish file names (`odpowiedz_lokalnie.py`, `skrypty/ai_odpowiedz.md`, `skrypty/`, `opowiesci/`) as **identifiers** — do not translate or change them. Error messages and dev-tool summaries are in English and are sufficient for navigation.

# ENVIRONMENT AND ARCHITECTURE (WXPYTHON)
- The project is fully based on the wxPython framework (native desktop GUI), with an emphasis on maximum accessibility for screen readers (A11y, e.g. NVDA). The entry point is `main.py`.
- OBJECT-ORIENTED CODE: Logic is divided into classes inheriting from `wx.Frame` (`main.py`) and `wx.Panel` (`gui_*.py`). Avoid procedural code.
- ACCESSIBILITY FIRST: Always ensure intuitive keyboard navigation. Use Sizers and refrain from creating custom, non-standard controls when the system-native ones do the job.
- SEED vs USER DATA (since 15.3): `dictionaries/` is the seed (single source for the engine, committed, and in the release package sits NEXT TO the exe — see `# DEPLOYMENT`). `runtime/`, `skrypty/`, `opowiesci/` (root), `*.env`, `error_log.txt` are user data — gitignored, outside the package. `runtime/skrypty/*.mode` are per-project metadata (hidden from the end user). **Since v17.0 (PyInstaller onedir) `runtime/` serves a DUAL role**: in the package it's the bundle folder (`--contents-directory runtime` → interpreter + libraries) AND a container for project metadata — both next to the exe, in one "intimidating" folder. Paths are computed by `sciezki.KATALOG_BAZOWY` (= dir(exe) when `sys.frozen`, otherwise dir(`__file__`)). Full architecture → [[reguly_architektury]].
- COMMUNICATION WITH THE USER (A11y): Short one-off notifications (successes, errors) → `wx.MessageBox`. Long technical messages → a `wx.Dialog` with a `wx.TextCtrl` (TE_READONLY) and a "Close" button. Avoid the "update the label and set focus" pattern as the main way of notifying the user.

# TERMINAL AND TESTING MANAGEMENT (BASH)
- You have full access to the terminal (Git Bash) and files. You may freely use Unix syntax, but you MUST follow the rules below:
1. VIRTUAL ENVIRONMENT (BASH): Bash does not honor VS Code's automatic `.venv` activation. Always use the full Unix path to the venv interpreter: `.venv/Scripts/python -c "..."` or `.venv/Scripts/python -m pytest ...`. Likewise for the package manager: `.venv/Scripts/pip install ...`.
2. NO BLOCKING THE TERMINAL (CRITICAL): Under no circumstances run the GUI application in a continuous manner (e.g. with an active `app.MainLoop()`). This suspends the process indefinitely — the session hangs until someone closes the window manually, and in an environment without desktop access, no one will close it. Test logic by running isolated snippets that terminate immediately. (In maintainer mode there is a second reason: a suspended process blocks screen-reader navigation.)
3. SAFE WXPYTHON TESTS (WITHOUT MAINLOOP): To check the interface without blocking the terminal, use the pattern that bypasses the event loop: `app = wx.App(False)`, call the constructor, and then use `frame.Destroy()`. This bypasses `MainLoop()` and the window closes immediately after the structure is checked.
4. CRITICAL SAFEGUARD (since v17.0): Running the frozen `.exe` (from `dist/` or `build/`) for logic testing is FORBIDDEN — it's a persistent GUI (breaks point 2, A11y). Additionally, `build/` is PyInstaller's WORKING directory (not a distribution): its exe won't even start (DLLs are only mounted in `dist/` → "cannot find python311.dll"). The only runnable target is `dist/` (with `dictionaries/`+`docs/` alongside) or an installed location. Test logic with isolated snippets from the SOURCE via `.venv/Scripts/python`. Also leave project metadata in `runtime/` (root, dev) alone.
5. THE `--no-pager` FLAG IN GIT (CRITICAL): Always run git commands that can trigger paging (e.g. `git diff`, `git log`, `git show`) with the `--no-pager` flag. Without it, git launches a pager that waits for an interactive keypress — in a non-interactive session this means a hang, and the output gets cluttered with terminal control sequences (in maintainer mode, additionally unreadable for NVDA).
6. GIT STATUS BEFORE COMMIT: Before every commit and before adding files, ALWAYS run `git status` to see the full state of the repository.
7. API KEYS (SINGLE-PROVIDER RUNTIME since 18.2): `golden_key.env` in the root (gitignored, physically on the developer's machine) holds ONE key, **`ANTHROPIC_API_KEY`** (`sk-ant-`) — the end user only needs this one. After the 18.0→18.2 consolidation, Claude Sonnet powers the ENTIRE AI engine — the runtime AND the translation dev-tooling (`buduj_wielojezyczne_ui.py`, `buduj_wielojezyczne_docs.py`, `buduj_wielojezyczne_tryby.py`, `tlumacz_ai.py`); **we do NOT hardcode the model name here** (single source: the `MODEL_TLUMACZ`/`MODEL_DOMYSLNY` constants in the code and the `model:` field in the recipes — today `claude-sonnet-5`) (full context + decisions → [[reguly_architektury]]). The agent **can and should** run the translation scripts directly (they load the key via `python-dotenv`) — do not push this step onto the user "because you don't have an API [key]". Stop only when the script returns "❌ No valid ANTHROPIC_API_KEY" or an HTTP 401/429 — then ask the user. After auto-translations, ALWAYS do a manual hallucination review ([[reguly_tlumaczen]]). **EXCEPTION — the only living consumer of OpenAI:** the dispatcher GitHub Actions workflow "Sami" (`issue_intake_sami.py`, issue intake) uses `gpt-4o-mini` with `OPENAI_API_KEY` (an Actions secret). `openai` is therefore back in `requirements.txt` (since 18.2.1) — for TRANSPARENCY and local bot debugging; the runtime does NOT import it, so the `.exe` and the end user's single key remain unchanged.
8. QUESTIONS AND COMMUNICATION: questions are welcome — break larger work into steps with decision points and ask instead of guessing. Otherwise you communicate normally. **In maintainer mode** a separate protocol applies (terminal length threshold, long content to a file) → [[reguly_architektury]], section "Communication with the user".

# APPLICATION VERSION NUMBER (since 13.4)
- SINGLE source of truth: the `VERSION` file in the repository root (plain text, e.g. `13.4-WIP` or `13.4`). You bump it **there only** — every other location resolves this value automatically.
- Every `dictionaries/<code>/gui/ui.yaml::app.wersja` holds a templated string like `"{numer_wersji} – Wersja Wydawnicza"` (the Polish package's value). Per language, you translate only the native suffix — **you don't touch the number** or the placeholder. The Constitution deliberately **does not enumerate** the suffix values (enumerating them entrenched calques): the single source is the package's `ui.yaml`, and the canon + forbidden variants are kept in the `przeglad_tlumaczen.py` checklist (public, in English, visible even without `memory/`). The meaning of the suffix: *software release*, NEVER print/editorial editing (ru `Издательская`, it `di Pubblicazione` = an error) nor tautology ("edition-edition").
- Mechanism: `i18n.t()` auto-injects the `numer_wersji=` kwarg from the VERSION file on every call, and `generuj_dokumentacje._rozwin_placeholdery` performs the same replace for docs/. `build_release.odczytaj_wersje()` reads `VERSION` as plain text and passes it to `iscc /DMyAppVersion=...`.
- If you see "?" in the GUI instead of a number — the VERSION file is missing (when absent, `i18n.NUMER_WERSJI` falls back to `"?"` so the application doesn't crash on startup).

# CODE AUDIT BEFORE CLOSING (lesson from v18.9.0)
Gates (leak gate, hardcode gate, `--waliduj`) guard CONTENT and literals — NOT concurrency or completeness of error handling. Green gates ≠ code ready: the v18.9 audit found 18 defects (7 high-severity) in code deemed polished. Before attempting to close, commission an audit from a subagent with a requirement of proof-by-execution for EVERY finding. Three classes to check on every new thread/GUI handler: (1) `sys.excepthook` does NOT cover threads — `threading.excepthook` is needed, AND its own try/except in the worker (without this, in a `--windowed` build the exception disappears without a log or dialog); (2) an `is_alive()` guard in every handler that mutates project state and at the ENTRY of the handler, not only in the `Enable` condition; (3) the baseline only blocks NEW hits — regenerate and read the diff both ways. Full checklist → [[reguly_architektury]].
