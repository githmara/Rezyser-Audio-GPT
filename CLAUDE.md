4. KRYTYCZNE ZABEZPIECZENIE (od v17.0): ZAKAZ uruchamiania zamrożonego `.exe` (z `dist/` ani `build/`) do testowania logiki — to ciągłe GUI (łamie pkt 2, A11y). Globalny handler crashy (`main._zainstaluj_obsluge_bledow`) → `error_log.txt` (marker rozpoznawany przez `issue_intake_sami`, który dla crashy pomija Lingua). # WORKFLOW RELEASE — direct-to-main (WYDANIA ROBI WYŁĄCZNIE MAINTAINER)
Kontrybutorze: **nie wydajesz Release'ów.** Nie pushuj na `main`, nie twórz tagów, nie odpalaj workflowa Release, nie bumpuj `VERSION` — przygotuj zmianę, przepuść bramki i zatrzymaj się. Niezmienniki, które musisz znać, jeśli tykasz cokolwiek wokół wydania:
- commit prosto na `main`, bez PR-ów (branch flow porzucony w v15.2.5); **tag powstaje WYŁĄCZNIE atomowo z Release** przez workflow `draft-release.yml` — nigdy lokalnym `git tag` ani `gh release create`;
- **force-push na `main` jest zakazany** (wąskie wyjątki tag-only → [[reguly_git_workflow]]);
- `RELEASE_NOTES.md` = single source of truth dla treści Release description (nie GitHub auto-generator). Nagłówek sekcji `## <wersja>` + bloki „What's new" / „Planned or deferred" po ANGIELSKU, polska diagnostyka pod nimi — bot wstawia tę sekcję jako body Release, gdzie locale=EN;
- `VERSION` bumpuje się **przed** regeneracją docs, a `docs/*.html` muszą wejść do release commita zregenerowane (`build_release.py` woła generator wewnętrznie i inaczej zostawia niezcommitowany diff);
- **ZAKAZ GitHub auto-close keywords** (`fix #N`, `closes #N`, `resolves #N`, …) w commit message, gdy issue ma zamknąć bot — bezpieczne formy: `(re: #N)`, `(addresses #N)`. Patrz [[reguly_github_bot]].

Pełna procedura wydawnicza (7 kroków, dwa assety z sumą SHA256, kolejność build-first, klauzula „bug-issue ma pierwszeństwo nad planowaną treścią") → [[reguly_git_workflow]], sekcja „Procedura release — 7 kroków".
